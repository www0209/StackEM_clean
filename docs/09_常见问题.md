# 09 常见问题

本文收集运行阶段可能遇到的问题。安装阶段的问题在 [02_安装.md](02_安装.md) 第 8 节。每个问题按“现象、原因、处理”的顺序写。

文中引用的日志数字登记在 `docs/checks/09_常见问题.jsonl`。

## 1. 先学会找出哪里出了错

无论遇到什么问题，第一步都是找到出错的那一步和它的报错信息。

1. 看汇总表。流程结束时屏幕末尾有一张步骤表，同样的内容存在 `~/stackem_work/outputs/logs/steps_<时间>.tsv` 里。查看最新的一张：

   ```bash
   cat $(ls -t ~/stackem_work/outputs/logs/steps_*.tsv | head -1)
   ```

   第三列是状态。`ok` 表示成功，`skipped` 表示被跳过，`FAILED(数字)` 表示失败，括号里是退出码。
2. 在日志里找到出错的位置：

   ```bash
   LOG=$(ls -t ~/stackem_work/outputs/logs/run_all_*.log | head -1)
   grep -n "Traceback\|FAILED\|Error\|Killed" $LOG
   ```

   第一行把最新日志的路径存进变量 `LOG`，第二行列出含有这些关键词的行和行号。
3. 查看出错位置前后的内容。下面的例子显示第 1200 到 1260 行，请把这两个数字换成上一步看到的行号前后各几十行：

   ```bash
   sed -n '1200,1260p' $LOG
   ```

Python 的报错以 `Traceback (most recent call last):` 开头，真正的原因在这一段的最后一行。

## 2. 内存不足

### 2.1 主内存不足

现象：某一步突然结束，屏幕上只有一个词 `Killed`，或者汇总表里这一步的状态是 `FAILED(137)`。日志里没有 Python 的报错。

原因：Linux 发现内存用尽时会直接杀掉占用内存最多的进程。退出码 137 就是被系统杀掉的标志。确认办法：

```bash
sudo dmesg | grep -i -E "out of memory|killed process" | tail -n 5
```

有输出就说明确实是内存不足。

处理，按顺序尝试：

1. 关掉其他占内存的程序。在 Windows 上包括浏览器和 COMSOL。
2. Windows 用户给 WSL 多分内存，做法见 [01_准备电脑与软件.md](01_准备电脑与软件.md) 的 3.3 节。参考机的 WSL 里可见内存约 30 GB，全部步骤都在这个内存下跑完。
3. 减少并行的进程数。参考求解器默认每个线程开一个进程，线程多的机器上进程多，占的内存也多。生成核数据集、E4 和 IBM 基准这三个入口有 `--workers` 参数，可以按 [04_复现实验_从零开始.md](04_复现实验_从零开始.md) 第 6 节的手动命令运行并加上例如 `--workers 8`。减少进程数只影响速度，不影响数值。E4 的耗时数字会因此改变，这一点要记下来。
4. 被杀的是大网表的 IBM 基准时，先只跑小的几个：

   ```bash
   bash scripts/run_ibmpg.sh ~/stackem_work/ibmpg/ibmpg1.spice ~/stackem_work/ibmpg/ibmpg2.spice
   ```

### 2.2 显存不足

现象：报错的最后一行含有 `CUDA out of memory`。

原因：显卡的显存不够，或者显存被别的程序占着。先看显存占用：

```bash
nvidia-smi
```

表格下半部分列出了占用显存的进程。

处理：

1. 关掉其他使用显卡的程序再重跑这一步。
2. 出错的是 E4 时，可以减小每批的轨数。按 04 号文档 6.2 节的手动命令运行 E4，加上 `--torch-bs 32 --tab-bs 256`。默认值分别是 64 和 1024。也可以用 `STACKEM_E4_SIZES=82,246,1000,5000` 去掉最大的规模，这样 E4 的比对结果会显示 `DIFF`，因为规模列表变了。
3. 出错的是训练时，说明显存放不下整个训练集。训练程序会把全部训练数据一次放进显存。这种情况下请改走路线 A。

参考机的显卡有 16 GB 显存，全部步骤都能跑完。更小的显存上没有测过。

## 3. 某一步被杀掉或失败

现象：汇总表里有 `FAILED`，最后一行是：

```text
StackEM flow finished: ...  -- FAILED steps: e4 teacher.e4
re-run them with:  STACKEM_ONLY=e4,teacher.e4 bash scripts/run_all.sh
```

说明：一个步骤失败不会让整个流程停下，后面的步骤照常运行。但依赖它的步骤也可能跟着失败或者得到不可信的结果。

处理：

1. 按第 1 节找到原因并解决。
2. 只重跑失败的步骤。日志最后一行已经给出了命令。路线 A 的读者把其中的 `run_all.sh` 换成 `run_with_released_weights.sh`，冒烟测试换成 `run_smoke.sh`：

   ```bash
   STACKEM_ONLY=e4,teacher.e4 bash scripts/run_with_released_weights.sh
   ```

3. 如果失败的是 `signoff`，之后所有用到轨宽的实验都要重跑，因为它们在没有签核结果时会改用默认轨宽。最简单的办法是整个重跑。
4. 如果失败的是 `e3`，同一算例的 `e7` 也要重跑。如果失败的是 `e2`，`comsol.export` 也要重跑。如果失败的是 `e4`，`figs.timing` 和 `teacher.compare` 也要重跑。

## 4. 显卡或处理器被别的任务占用，耗时失真

现象：E4 的耗时比参考结果慢很多，或者两次运行相差很大。

原因：E4 是测速实验。显卡或处理器同时在跑别的任务时，它测到的时间就不再反映这台机器的真实速度。参考机的日志里有一个现成的例子：E5 这一步在整条流程里运行时用了 184 秒，之后单独重跑一次用了 173 秒。两次相差 11 秒，可以作为机器空闲时正常波动幅度的参考。

处理：

1. 运行期间不要同时启动第二个 StackEM 流程，也不要运行别的计算程序。一次只跑一个任务。
2. 运行前确认显卡空闲：`nvidia-smi` 的 `GPU-Util` 一栏应当接近 0。
3. 确认处理器空闲：`cat /proc/loadavg` 的前三个数应当远小于线程数。
4. Windows 用户注意后台的杀毒扫描、系统更新和游戏。
5. 怀疑耗时失真时，在空闲状态下只重跑测速相关的步骤：

   ```bash
   STACKEM_ONLY=e4,teacher.e4,teacher.compare,figs.timing bash scripts/run_with_released_weights.sh
   ```

耗时失真只影响 E4 的时间和各摘要里的秒数，不影响任何精度数字和物理结论，也不影响 `check_results.py` 的比对，因为耗时不参与比较。

## 5. WSL 自己停了

现象：第二天回来发现 tmux 会话不见了，`tmux ls` 显示 `no server running`，任务没有跑完。

原因有三种。

| 原因 | 怎样确认 | 处理 |
|---|---|---|
| Windows 进入了睡眠或休眠 | 电脑当时是黑屏的 | 在 Windows 的“设置、系统、电源”里把睡眠时间改成“从不”，笔记本电脑接上电源 |
| Windows 自动更新后重启了 | 开机后所有窗口都没了 | 在“设置、Windows 更新”里暂停更新，跑完再恢复 |
| 所有 Ubuntu 窗口都关闭后 WSL 自动停止 | 你关掉了全部终端窗口 | 跑长任务期间至少留一个 Ubuntu 窗口开着，最小化即可 |

第三种情况需要多解释一句：tmux 能保证关掉窗口后任务继续，但前提是 WSL 这台虚拟机本身还在运行。稳妥的做法是留一个 Ubuntu 窗口不关。

WSL 停止后任务会中断，已经完成的步骤的结果都还在硬盘上。按下一节续跑。

## 6. 中断以后怎样接着跑

流程没有自动续跑的功能，但每个步骤的结果都是独立保存的，所以可以手动只跑没完成的部分。

1. 找出最后完成到哪一步。看最新日志里的步骤标题：

   ```bash
   grep -E "^=+ |^\[done\]" $(ls -t ~/stackem_work/outputs/logs/run_all_*.log | head -1) | tail -n 6
   ```

   最后一个有标题却没有对应 `[done]` 行的步骤，就是中断时正在运行的步骤。
2. 从这一步开始，把它和它之后的所有步骤写进 `STACKEM_ONLY`。步骤的完整顺序见 04 号文档第 1 节。例如在 `e6` 中断：

   ```bash
   STACKEM_ONLY=e6,e8,quad4,dense3,teacher,ablation,ibmpg,comsol,tables,figs bash scripts/run_with_released_weights.sh
   ```

   路线 B 的读者用 `run_all.sh`。这时一定要用 `STACKEM_ONLY` 明确列出要跑的步骤，否则 `run_all.sh` 会从生成核数据集开始全部重来。
3. 中断时正在运行的那一步可能留下了不完整的文件，重跑时会被覆盖，不需要手动删除。

训练中断的情况：教师训练、蒸馏和消融训练都不能从中间接着训练，只能把这一步整个重跑。训练过程中 `skn_best.npz` 会随着验证误差的改善不断更新，但中断时留下的这个文件是没训练完的网络，不要用它继续后面的实验。

路线 B 里已经完成的训练不需要重做。例如教师和学生都已训练完，只是后面的实验中断了，那就在 `STACKEM_ONLY` 里只列实验步骤，不要列 `kernels`、`train_teacher`、`distill`。

## 7. 硬盘空间不够

现象：报错里含有 `No space left on device`。

查看剩余空间和各文件夹的大小：

```bash
df -h ~
du -sh ~/stackem_work/* ~/.cache/pip 2>/dev/null
```

可以安全删除的东西，按建议的先后顺序：

| 内容 | 命令 | 说明 |
|---|---|---|
| pip 的下载缓存 | `rm -rf ~/.cache/pip` | 可以有好几 GB，删掉不影响已装好的环境 |
| 冒烟测试的输出 | `rm -rf ~/stackem_work/outputs_smoke` | 确认冒烟测试通过后就没用了 |
| IBM 基准的压缩包 | `rm ~/stackem_work/ibmpg/*.bz2` | 解压后的文件还在，不影响运行 |
| 各实验文件夹里的 HotSpot 草稿 | `find ~/stackem_work/outputs -type d -name "hotspot*" -prune -exec rm -rf {} +` | 每个实验保存了自己的 HotSpot 输入输出，流程结束后可以删 |
| 图表索引文件夹 | `rm -rf ~/stackem_work/outputs/*/figs_index` | 里面全是副本，可以随时用 `STACKEM_ONLY=figs` 重建 |
| 核训练集，只有路线 B 有 | `rm ~/stackem_work/outputs/base3/kernels/kernels_train.npz` | 训练和蒸馏都完成以后才能删。删掉后想重新训练就要重新生成 |

Windows 用户还要知道：WSL 的整个 Linux 文件系统是 C 盘上的一个虚拟磁盘文件，所以 C 盘的剩余空间才是真正的上限。在 Linux 里删除文件后这个虚拟磁盘文件不会自动变小。C 盘紧张时，首先要做的是清理 C 盘本身。

## 8. 删除输出，从头再来

只想重跑某一个实验时不需要删除任何东西，新结果会覆盖旧结果。下面是需要彻底清理的几种情况。

| 目的 | 命令 |
|---|---|
| 删除某一个实验的结果，例如 base3 的 E4 | `rm -rf ~/stackem_work/outputs/base3/e4` |
| 删除一个算例的全部结果 | `rm -rf ~/stackem_work/outputs/quad4` |
| 删除全部正式运行的输出 | `rm -rf ~/stackem_work/outputs` |
| 保留旧的输出，新的一次运行写到别处 | `STACKEM_ROOT=$HOME/stackem_work/outputs_run2 bash scripts/run_with_released_weights.sh` |
| 连环境一起删除，回到安装之前 | `rm -rf ~/stackem_work` |

`rm -rf` 删除的东西无法恢复，回车之前请再看一眼路径。仓库 `~/StackEM_clean` 不需要删除，流程不会往里面写任何东西。

路线 B 的读者注意：删除 `~/stackem_work/outputs/base3` 会把核训练集和你自己训练的网络一起删掉。想保留它们时，先把这三个文件夹移到别处：

```bash
mkdir -p ~/stackem_work/keep
cp -r ~/stackem_work/outputs/base3/kernels ~/stackem_work/outputs/base3/skn ~/stackem_work/outputs/base3/skn_distill ~/stackem_work/keep/
```

用了第四行那种写法以后，比对时要指定同一个目录：`python tools/check_results.py --root ~/stackem_work/outputs_run2`。

## 9. 比对出现 DIFF

先读 [03_复现实验_使用发布的权重.md](03_复现实验_使用发布的权重.md) 第 7 节和 04 号文档第 5 节。最常见的三种原因：

1. 路线 B 之后忘了加 `--retrained`。
2. 在没有签核结果的情况下单独跑了某个实验。日志里会有 `[warn] no sign-off sizing found`。先跑 `signoff`，再重跑那个实验。
3. 某一步中途失败，留下的是上一次运行的旧文件。按第 3 节重跑。

用 `-v` 可以看到每一个超出容差的数字和它在文件里的位置：

```bash
python tools/check_results.py -v | less
```

## 10. 其他运行问题

### 10.1 提示找不到 HotSpot

现象：报错里有 `FileNotFoundError`，路径指向 `stackem_work/HotSpot`。

原因：HotSpot 没有编译成功，或者工作目录不在默认位置。检查 `ls ~/stackem_work/HotSpot/hotspot`。文件不存在就重新运行安装脚本。如果你把 HotSpot 放在别处，运行时加上 `STACKEM_HOTSPOT=<目录>`。

### 10.2 `ibmpg` 这一组显示 `skipped(no netlist)`

原因：`~/stackem_work/ibmpg` 里没有网表。按 [05_IBM基准与COMSOL.md](05_IBM基准与COMSOL.md) 的 1.2 节下载。

### 10.3 `comsol.compare` 打印了一行提示就结束了

这是正常的。没有 COMSOL 的结果文件时这一步什么也不做，状态仍然是 `ok`。

### 10.4 蒸馏这一步失败，提示需要 PyTorch

现象：`PyTorch is required for the distillation`。原因是虚拟环境里没有 PyTorch。检查 `python -c "import torch"`，报错的话按 02 号文档重新安装。只有路线 B 会遇到这个问题。

### 10.5 运行时出现大量 RuntimeWarning

`RuntimeWarning: overflow encountered in exp` 这样的警告在参考机的日志里也有，不影响结果。只有以 `Traceback` 开头的才是错误。

### 10.6 想确认某一步用的是显卡还是处理器

| 步骤 | 看哪里 |
|---|---|
| 训练和蒸馏 | 日志里以 `device` 开头的一行，`device cuda` 表示显卡 |
| IBM 基准 | 日志里 `closure (torch/cuda, ...)` 或 `closure (numpy/cpu, ...)`，以及摘要的 `closure_backend` |
| E4、E5 | 摘要文件 `e4_timing.json`、`e5_summary.json` 里的 `device` 字段 |

E2、E3、E7、E8 的闭合本来就用 numpy 在处理器上运行，与有没有显卡无关。

### 10.7 脚本提示 `Permission denied`

原因多半是仓库放在了 Windows 盘上，也就是 `/mnt/c` 之下。把仓库移到 Linux 的家目录。所有脚本都用 `bash scripts/xxx.sh` 的方式运行，不需要给脚本加可执行权限。

## 11. 怎样引用数字

你可能需要在报告或论文里引用本项目的数字。请遵守下面几条。

1. 说明数字的来源是哪一种。`reference_results/` 里的数字是参考机上的发布结果。`~/stackem_work/outputs/` 里的数字是你自己的运行结果。两者不要混用，尤其是耗时。
2. 引用耗时的时候写明硬件。参考机是 AMD Ryzen 9 9950X，16 核 32 线程，显卡是 NVIDIA GeForce RTX 4070 Ti SUPER 16 GB。所有耗时都是单次测量。
3. 引用精度的时候写明是哪一个算例、哪一种情形、哪一个统计量。例如“base3，完整三维情形，D3 上成核时间相对误差的中位数”。同一个实验里有中位数、90 分位和最大值，不同芯片的数值也不同，不能笼统地说“误差是多少”。
4. 引用精度的时候写明用的是哪一个网络。发布的学生网络和你自己训练的学生网络是两个不同的网络，数字会有小的差别。
5. 真值与预测要分清。E3、E6 里的最早成核时间和成核轨数是参考求解器给出的真值。E2、E8、IBM 基准里的误差是 StackEM 相对于这个真值的偏差。
6. COMSOL 的计时只有 246 条轨是实测，更大规模的数字是外推。引用时要说明。
7. 给出数字所在的文件和键。每个摘要 JSON 都是普通的文本文件，可以这样取出一个值：

   ```bash
   cd ~/StackEM_clean
   python -c "import json; d=json.load(open('reference_results/base3/e2/e2_summary.json')); print(d['full']['metrics']['D3']['tnuc_rel_median'])"
   ```

   这条命令打印 base3 完整三维情形下 D3 的误差中位数，结果是 `0.017154456698170298`，也就是 1.72 %。
8. 文档里出现的每个数字都有对应的核对条目，写在 `docs/checks/` 下与文档同名的 `.jsonl` 文件里，每行给出数字、它所在的文件和取值路径。全部复核一遍的命令是：

   ```bash
   cd ~/StackEM_clean
   python3 tools/verify_docs.py
   ```

   最后一行应当是 `N checks, N passed, 0 failed`。想查某个数字出自哪里，在对应的 `.jsonl` 文件里搜索这个数字即可。

## 12. 还是解决不了

请准备好下面四样东西再求助，它们能让别人很快看出问题所在。

1. 安装时的输出 `~/StackEM_clean/setup_env.log`。
2. 出错那次运行的日志 `~/stackem_work/outputs/logs/run_all_<时间>.log` 和同名的 `steps_<时间>.tsv`。
3. 下面这条命令的输出，它列出 Python、各软件包和显卡的情况：

   ```bash
   python -c "import sys, numpy, scipy, torch; print(sys.version); print(numpy.__version__, scipy.__version__, torch.__version__, torch.cuda.is_available())"
   ```

4. 机器的基本情况：`nproc`、`free -g`、`df -h ~` 和 `nvidia-smi` 的输出。

## 安装时用到了别的 Python 版本

`scripts/setup_env.sh` 第 2 步会打印一行 `interpreter: ...`，显示虚拟环境建在哪个 Python 上。参考结果是用 Python 3.11 产生的。脚本按下面的顺序找解释器：先找命令 `python3.11`，找不到再到 conda 的各个环境里找 `python3.11`，都没有才用系统的 `python3`，这时会打印一行 `[warn] not Python 3.11`。

其他版本的 Python 通常也能装上同样版本的软件包并跑通全部步骤，只是与参考结果逐位一致的保证只对 3.11 成立。想换成 3.11，先删掉已有的虚拟环境再重新安装：

```bash
rm -rf ~/stackem_work/venv
bash scripts/setup_env.sh
```

也可以用环境变量直接指定解释器，例如 `STACKEM_PYTHON_BIN=/path/to/python3.11 bash scripts/setup_env.sh`。虚拟环境已经存在时脚本不会重建它，所以换解释器之前一定要先删。
